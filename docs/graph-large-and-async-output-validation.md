# 大规模图规划与增广 ME 异步输出验证

后续的首次捕获优化与最新对照见 [图合成首次下单捕获优化](graph-capture-performance.md)。本页保留本轮原始数据。

2026-09-24。基于 `feat/ae-cycle-support` 的 `f3a56640`，独立测试服使用 Java 21.0.3、
Forge 47.3.7、AE 15.4.10、6 GiB 堆和实际 `gtladditions-3.2.8Custom_SubSpace-fix2.jar`。
用户反馈来自原版 Core 的转述，没有对应存档、日志或触发步骤。以下区分可重复的问题与尚未确认的反馈。

## 异步输出的问题与修复

原版总成先返回“已接收”，随后才由全局写入线程读取产物并放入累加器。
保存等待这个线程最多 500 ms；超时返回值被调用方忽略，仍会继续序列化不完整的 `buffer`。
掉落物保存原先跳过异步刷新，移除总成还会直接清空累加器。
此外，接收和入网后的数量变化没有在这些路径显式标记区块需要保存；流体转 AE key 时遗漏 NBT。
这些代码在 `13a7328e` 上游基线就存在，不由本轮图引擎引入。

修复后：

- 产物接收时立即解析确定的 key、数量，写入机器持有的账本，然后才确认接收。
  后台不再读取或重新采样可变 Ingredient，省去逐配方排队任务。
- 后台仍可批量转移账本；取走数量和发布到交接队列使用同一个机器级锁。
  保存直接刷新自己的账本，不受其他总成的写入队列或超时影响。
- 普通保存、掉落物保存和移除均刷新暂存数据；接收和实际入网后标记保存。
- 保留流体 NBT，物品和流体数量使用 long。
- 保留公开提交、刷新方法及 `FLUSH_TIMEOUT` 字段的二进制入口，刷新已不依赖此超时。

入网仍使用 `StorageHelper.poweredInsert` 的实际接收量扣减 buffer；
没有用模拟结果或规划预期值消除真实物品。

### 验证

独立 JVM 使用真实 AE key/NBT，验证了堵塞写入线程时立即保存、提交后修改列表/数量、带 NBT 的物品和流体、
30 亿流体、并发生产/转移/保存，以及写入服务关闭后重建。4 个生产线程各提交一万次、每次 30 亿，
最终合计 `120000000000000`，没有丢失或重复。

专用测试服使用真实总成，将全局写入线程人为堵塞，并将旧超时临时设为 1 ms 以缩短测试。
修复版普通保存和掉落物保存均记录完整的 30 亿带 NBT 物品。
使用修正后同一夹具重跑旧包，两种保存均为 `saved=0 keys={}`；
普通保存明确出现 flush 超时日志。此前修复包写入的 30 亿带 NBT 物品在完整停服/重启后仍存在。
测试脚本通过指定 `create(ItemStack)` 重载构造原料，避免 KubeJS 自动转换为 Ingredient 时丢失测试 NBT。
初次错误构造夹具的统计不作为 NBT 验证证据。

真实 AE CPU → 可控外部处理提供者 → 真实异步输出总成 → AE 网络，结果如下：

| 场景 | 最终原料 | 最终产物 | 已派发批数 |
| --- | ---: | ---: | ---: |
| 正常完成 100 个产物 | 900 | 100 | 100 |
| 派发后取消，产物稍后返回 | 999 | 1 | 1 |

两项都从 1000 原料开始。外部提供者按 1:1 处理，用于控制返回时序；CPU、库存挂载、ME 路由和输出总成为实际实现。
存储先拒绝入库，随后每次最多接收 7 个；中途对暂存中的总成做真实 NBT 保存/加载。
这些测试证明了该返回路径的物料守恒，没有模拟运行整套 GT 巨构配方。

仍不能将上述触发条件直接等同于网友描述的“概率吞物品”。没有重现任意真实机器、任意附属异常处理，
也没有测试断电式进程崩溃时多个区块文件的原子落盘。

额外用真实总成测试每样本一万次接收、每次 100 个带 NBT 物品，旧包和最终包均完整保存一百万个。
首轮之后三个样本的中位数：旧包接收 9.40 ms、接收加刷新 18.21 ms；最终包接收 17.56 ms、接收加刷新 17.63 ms。
接收阶段多做约 0.82 微秒/次，完整处理时间接近；这是将物品所有权立即落到机器账本的代价。
两包在独立 JVM 测量，样本很少，不据此宣称整体吞吐显著提升。

## 图规划改进

1. 捕获的确定配方交给后台进行优先级排序和生产者索引；工作保留进度并检查取消/预算，完成后才发布共享索引。
   主线程仍处理实时样板方法和库存，增量捕获总额度仍为 2 ms/tick。
2. 修复大结构缓存自淘汰：32,768 层链的资源数加配方数超过 65,536，原先刚放入目录缓存就被移除。
   编译结果也有类似的 32,768 节点门槛。现在允许保留一个已通过请求限制的大条目；新条目替换时继续淘汰旧条目，
   没有无限积累大图。
3. NBT 规范编码改为复用 StringBuilder；通常只读取一次且容易发生哈希碰撞的编码样板定义，不再挤占物料 key 的 LRU。
   指纹编码格式、实际样板语义、最后的物料验证保持一致。

## 一万亿物品订单压测

测试仅规划，不实际制造一万亿物品。每种拓扑先发一次请求，再执行四次重复请求。
同 JVM 串行交替 MAX_FAST/Graph，用独立解释器检查投入、配方执行次数和目标数量。
均启用相同的 JFR profile 与诊断日志。只有四次重复样本，不据此声称稳定的 p95。

最终包同 JVM 重复请求中位数，单位 ms：

| 拓扑 | MAX_FAST | Graph |
| --- | ---: | ---: |
| 8,192 层链 | 131.55 | 104.53 |
| 16,384 层链 | 145.59 | 173.11 |
| 32,768 层链 | 319.00 | 494.95 |
| 512 层 × 32 路共享依赖 | 372.51 | 398.82 |

前三项材料、配方次数和 bytes 相同。共享依赖两边选择了不同的合法舍入方案，不能视为相同工作量：
MAX_FAST 使用 `1000000015212` 原料，Graph 使用 `1000000007816`，均通过独立验证。
初轮共享图只额外准备 4096 原料，两个引擎都报告不足；最终改为按结构规模准备足够余量，保留初轮记录。

同样的 32,768 层链，本轮修改前连续下单中位数 **14429.46 ms**，修改后 **494.95 ms**，约减少 96.6%。
这是两个 JVM 的前后补充比较；同期 MAX_FAST 为 353.15 → 319.00 ms，不能把全部波动归因于补丁。
缓存命中日志与消失的重建阶段直接支持自淘汰修复的作用。

首次请求仍明显慢于 MAX_FAST：

| 链深度 | 修改前 Graph | 修改后 Graph | 同场 MAX_FAST |
| --- | ---: | ---: | ---: |
| 8,192 | 4988.27 | 3940.63 | 725.58 |
| 16,384 | 6853.21 | 5950.03 | 420.84 |
| 32,768 | 14445.51 | 10215.23 | 815.15 |

这些是每种拓扑一次首次请求，包含 JIT/GC 等环境差异。快照依旧跨 tick，不能将经过的秒数当作纯计算时间。
32,768 层热请求的快照实际工作约 8–9 ms，按 2 ms/tick 分摊仍可能产生 150–200 ms 等待。
验证和最终 AE 计划组装也仍有开销。本轮没有消除这些限制，也没有关闭验证来改善成绩。

65,536 层在默认 32 MiB 请求预算下受控返回 `GRAPH_MEMORY_LIMIT`，没有提交或取料。
该次等待约 20.74 秒，其中快照实际工作约 883 ms；这说明极大结构的拒绝时机和首次捕获仍需改进。

仅在隔离服把请求预算设为 128 MiB 后，同一 65,536 层 / 一万亿订单通过三组新旧对照，
物料和配方次数一致，独立解释器全部通过。首次 Graph 25.36 秒、MAX_FAST 2.65 秒；
两次重复请求 Graph 1.170/0.965 秒，MAX_FAST 0.966/0.822 秒。没有修改发布默认预算。

此规模还出现 CPU 费用的浮点舍入差异。链的独立精确公式为
`(2 × depth + 1) × amount + 8 × (depth + 1)`，得到 `131073000000524296`；
Graph 与公式一致，旧算法为 `131073000000524288`，少 8 字节。
检查实际 AE 的 `CraftingSimulationState` 字节码确认其用 double 累加 bytes，最后 ceil 后转 long。
测试仍保留 `bytes_equal=false`，不将这三组计为完全一致；这是费用精度差异，不是丢失物品。

### 如何理解内存预算

32/128 MiB 是新引擎对每请求数据结构的估算预算，不是游戏堆大小，也不是 JVM 的真实保留内存采样。
旧 MAX_FAST 没有同口径限制，两边测试 JVM 堆都为 6 GiB。
65,536 层新引擎累计估算约 59.5 MiB；快照、执行步骤与验证状态确有额外数据，
但本次没有测出新旧引擎各自真实堆占用的倍数。也不能用热请求 `peakReservedBytes=0` 推断它不占内存，
热请求会复用先前分配的缓存。
