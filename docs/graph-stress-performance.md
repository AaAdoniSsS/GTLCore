## 测量方式

- 同一台 Ryzen 9 7945HX、Windows x64、Corretto 20.0.2.1、6 GiB 服务端堆，Forge 47.3.7 / AE 15.4.10。
- 旧算法为同一 Core 基线中的 `MAX_FAST`，不是原版 AE 的未优化递归算法。
- 同一 JVM、同一网络、同一库存和样板；串行 A/B，每次交替顺序。两个引擎均开启诊断日志。
- 每组请求 1,048,576 个产物，一次首次请求、七次重复请求。每次的计时不含样本间隔和事后的独立验算。
- 四条链深度为 128 / 512 / 2,048 / 8,192；共享图每层八路，深度为 8 / 16 / 24 / 64。
- 使用 NBT 不同的纸作为资源、真实 `AEProcessingPattern`、实际网络库存及生产规划入口。
  提供者由测试探针挂载，不允许投料。因此测的是规划，不是实际机器生产耗时、整包加载或多人服务器 TPS。
- Graph 总耗时包括快照、等待、构图、求解、验证、容量和计划生成；不能只拿求解区间和旧算法总耗时相比。

脚本和复现方式见 [服务端探针说明](../tools/graph-server-probe/README.md)。
最终原始日志 `.local/server-stress-delivery.log`，逐样本 JSON `.local/graph-stress-delivery.json`。
本次总计 64 对请求；每个新旧计划都在计时后通过独立配方解释器检查逐步库存和目标产物。
CPU 提交/派发另有真实循环回归，不与这组只规划的压力测试混为一谈。

2,048 层 Graph 相对优化前减少约 83.3%；8,192 层减少约 72.1%，但后者仍约为旧算法的 2.03 倍。
上表 56 对请求的产物、used/missing/emitted、simulation、配方次数和 CPU bytes 全部一致。
数量很大没有导致逐件展开，8,192 层也没有出现栈溢出。

样本量只有七个，最近秩 p95 就是本组最大值；详细极值保留在 JSON，不当作稳定尾延迟保证。
不同轮次有 JIT、日志和调度波动，尤其毫秒级差异不能外推为整包固定加速倍数。

两边分别使用 1,048,848 / 1,048,720 个原料，Graph 少用 128 个，配方次数也有差别。
这是共享需求聚合后取整与按请求模板取整的差异；两份计划均在八次独立验算中逐步可执行、产出足够。
结果保留 `materials_equal=false / recipes_equal=false / bytes_equal=false`，没有隐藏差异。

## 首次请求仍存在的差距

这是各拓扑首次使用的单样本，不是七次热请求的中位数。第一组还包含首次类加载和 JIT。

| 拓扑 | 旧总耗时 ms | Graph 总耗时 ms | Graph 实际快照工作 ms |
| --- | ---: | ---: | ---: |
| 128 层链 | 171.24 | 386.04 | 见 JSON |
| 512 层链 | 19.05 | 363.04 | 见 JSON |
| 2,048 层链 | 58.91 | 929.32 | 见 JSON |
| 8,192 层链 | 165.28 | 3,670.67 | 144.53 |

8,192 层的快照实际执行约 145 ms，但总计约 3.67 秒，因为世界/样板方法在主线程、共用每 tick 2 ms 额度。
热请求快照降至约 2.77 ms，仍会跨 tick，解释了极深链的一部分额外等待。
本轮没有通过抬高主线程预算、后台读取世界或放弃权限/库存复核来掩盖这部分代价。
后续重点是减少首次快照内的规范化和序列化工作，进一步分离纯数据计算与必须在世界线程执行的操作。

## 具体改动

1. 非循环、单配方且输入输出不重叠的区域直接传播精确需求。循环仍使用原有有界求解；最终具体执行顺序仍通过验证器。
2. 普通 Batch 的前缀需求、净变化、峰值直接合并进 Sequence，减少逐配方三份临时 Map 的生成和复制。
3. 快照每 32 个小步共用计时区间；同一步的样板指纹只计算一次；模糊库存检查只保留每个主键的一个代表。
   库存模拟提取、权限、输入与输出复核保留。
4. 后台每片操作上限从 512 改为 4,096，实际 2 ms 期限和 FIFO 续算保持，避免大量极短任务切换。
5. 材料容量按相同 `amountPerByte` 合并后统一精确取整；不按每个资源重复做分数约分。
6. 修复共享图节点计费：同一个输入模板被多个路径引用时共享内部节点，终端仍按展开父请求收费。

最初 24 层共享图的材料和配方次数已相同，但旧 bytes 为 38,799,944，新实现错误地收取 240,123,896。
原因是把共享子图的整棵子树费用重复累加。修复后该用例两边均为 38,799,944，
并新增 8 / 16 / 24 层的 71 / 201 / 329 个计费节点回归。没有用“更少 bytes”冒充性能收益。
