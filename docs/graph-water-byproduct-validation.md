# 无限水元件与副产物回路验证（2026-09-24）

本文记录水回路修复时的构建；后续跨阶段执行器改动见 [流水线执行器验证](graph-pipeline-validation.md)。

本次按用户提供的 ExtendedAE「ME 无限水元件」构造等价配方。没有得到原问题的具体样板、
机器或故障存档，不能把本测试通过解释为已复现并修复那一例旧执行器卡死。

## 场景与证据边界

隔离 Forge 47.3.7 / Java 21 服务端，AE2 15.4.10，安装用户的 ADD 3.2.8Custom_SubSpace-fix2、
ExtendedAE、MAE2 等现有测试依赖。真实驱动器挂载 `expatternprovider:infinity_cell`；
Core 的 `InfinityCellMixin` 令它报告 `Long.MAX_VALUE` 库存。测试先验证缓存数量和实际模拟提取。

样板通过真实 AE 接口注册。有限原料来自可计数的测试存储，处理过程由测试供应器模拟；
真实 AE 库存、CPU、图执行器、旧执行器和产物回到网络的路径参与验证。
这里没有真实 GT 机器的配方运行、输出总成或堵塞管道，因此不能覆盖特定机器的回料故障。

等价配方为：

```text
R + 1000 mB 水 → I
I → P + 500 / 1000 / 2000 mB 水
```

分别测试仅 P 为主产物，以及额外装入水为主产物的等价样板（使水可被独立请求）。
普通 AE 只把第一输出登记为可合成项，不能只交换输出顺序后仍假定 P 可以发起请求。

请求量：9、97、100,000,000、100,000,017、1,000,000,000,000；有限原料恰好够用。
另测 `R + 水 → P`、`P + S → Q + 水`，没有 S 但已有无限水时，应只执行第一条。
9 份订单实际执行，大额订单只验证规划、原料和配方次数，不把它们说成已完成实际生产。

MAX_FAST 用真实 `CraftingCalculation` 产生旧 `CraftingPlan`，提交同一 CPU 后走旧执行器；
探针检查 `MaxFastExecutor.execute` 与 `CraftingCpuLogic.executeCrafting` 的调用计数。
两次测试之间等待 AE 库存缓存刷新，避免把测试重置尚未同步误报成旧算法缺料。

## 修正的新引擎边界问题

1. 多配方循环先按并行数放大，再向上取整，会把最后不足一批的订单算成整批。
   `1 亿 + 17`、2 路并行、每次回水 2000 mB 在原构建触发搜索上限；修正为完整批次加精确尾批。
   不额外消耗原料，也不按订单数量展开计划。
2. 重规划时，网络的 `Long.MAX_VALUE` 可用水与 CPU 实际持有/在途水直接相加会溢出。
   现在仅对规划可用量取可表达的下界；实际所有权、取料、返还、产物及守恒仍用精确运算。
3. 回退搜索把整个网络库存当作 CPU 内部余额，错误地限制正增量副产物的“剩余空间”。
   现在搜索中的假设余额使用大整数，最后只提取具体执行路径需要的初始物料。
   最终验证仍检查每个执行前缀、真实最大持有量和 `long` 边界。

另设运行时故障注入：扣住应返回的水，验证它会等待；再补回水，验证能继续，且等待期间的
任务快照恢复不会重复投料。这种等待是正确行为，不是本次要消除的 bug，也不是原报告的已知原因。

## 当前执行器的流水线边界

纯无环、无保种要求的平铺计划使用 `DagScheduler`。新增用例让上游接单 100 份，
只返回 10 份中间产物且副产物完全未回；下游立即投入这 10 份。存档恢复后再返回 5 份，
下游继续投入 5 份。上游与下游可同时在途，副产物债务保留到最终结清。

含循环、保种或不符合平铺条件的计划使用 `PlanCursor`。同一配方可以向多台机器派发，
切换到不同配方时仍有全阶段产物屏障；连任务中的普通前置步骤也受到限制。
现有用例验证了前置步骤仅部分返回时，下一个循环配方不会放行。
因此“同配方并行”已经支持，“含环任务的通用跨阶段流水线”仍未实现，本构建没有改动这一点。
