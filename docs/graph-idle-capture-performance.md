# 图合成捕获等待与精确输入优化

2026-09-24，基于已推送的 `641aa48c`；延续 [上一轮首次捕获优化](graph-capture-performance.md)。

## 为什么 MAX_FAST 的快照较快

原版 AE 的 `NetworkCraftingSimulationState` 构造函数复制库存数量，但当前 Core 的
`NetworkCraftingSimulationStateMixin` 已跳过这次整表复制：保留 `getCachedInventory()` 返回的引用，
在规划期间按需查询；开启模拟提取或存在手工库存预留时再调用原库存的模拟提取。
因此，不能把原版 AE 的库存复制流程当作当前 MAX_FAST 的实际实现。
Graph 的 `snapshot` 计时还包含依赖发现、有效样板捕获、输入选择、容器返还与相关资源数量采集；
两个路径的准备工作及线程边界不同。

Core 的 `CraftingCalculationMixin` 同时取消了原版 AE 按 tick 暂停/恢复计算的握手：
`handlePausing` 只检查线程中断，`simulateFor` 只观察完成状态，后台任务可连续执行。
Graph 的后台求解也不按 tick 发放额度；Graph 额外受 tick 调度影响的是主线程捕获阶段。
这不代表 MAX_FAST 不受 CPU 竞争、GC、后台任务排队或请求发起/提交的主线程延迟影响。

这轮发现并处理了两个具体问题：

1. 原版加工样板的输入只接受精确 AEKey，但 Graph 仍对每张样板扫描库存中同物品的 NBT 变体。
   这会产生“样板数 × 库存变体数”的重复校验。参考 MAX_FAST 的精确输入分支，
   现在只有实际类为 `AEProcessingPattern` 且每个输入均为其原生 `Input` 时跳过模糊扫描。
   仍校验声明的输入；附属包装、自定义输入及可替代输入保留完整路径。
   精确输入不再把无关库存变体加入目录失效条件，实际库存数量仍重新采集。
2. 原来即使服务器大部分时间空闲，捕获也只有 2 ms/tick 的额度。
   上一版 65,536 层的捕获经过约 5,301 ms，其中约 5,069 ms 在等待。
   现在在 `MinecraftServer.waitUntilNextTick` 期间，原版普通任务和区块任务都暂时无事可做后，
   利用剩余空闲时间继续捕获。每次最多申请 1 ms，保留下一 tick 前的 1 ms 余量，
   每段之后重新让原版轮询任务；不设置会延长原版 tick 截止时间的 `mayHaveDelayedTasks`。
   忙碌服务器没有这部分空闲额度，仍使用原来的 2 ms/tick 路径。

这些时间额度是协作式检查，不能中断正在执行的附属回调、GC 或 JIT；并非绝不超时的硬保证。
首次类加载、提供者的单次慢调用仍可能产生较长分段，日志保留最长分段计时。

## 其他改动与线程边界

捕获完成时把已结束写入的自有集合交给只读视图，省去大型哈希表的整表重建。
后续请求使用新集合；目录复用及提供者变更测试检查已发布资源、依赖和库存没有被改变。
计划计数直接处理平铺批次，减少遍历帧；每次批量处理至多 32 个操作且逐项检查预算。
节点费用先以受检查的 long 计数，最终费用仍使用精确 BigInteger；摘要减少重复 BigInteger 运算。

库存、提供者、样板判断及容器回调仍只在服务器主线程执行。
指纹编码、目录编译、图求解和计划处理继续在后台执行。
直接复制整个 AE 对象引用不能隔离附属内部状态；深拷贝也不能自动把可访问世界的任意回调变成纯函数。
因此本次没有并行读取实时库存或任意附属样板，也没有引入第二套全网络可变状态镜像。
提交时的样板核验、实际取料及物料守恒检查保留。

## 密集 NBT 库存与忙服边界

真实 AE 输入的归一化测试加入 8,192 种纸的 NBT 变体、30 亿输入数量，比较原生精确路径与
强制走通用路径的包装样板。结果的配方 ID、槽位、输入输出完全一致，预算计数从 8,196 降到 4；
通用包装仍执行全部校验。这是操作数对照，不是耗时倍率。

实际服务端另测 128 层原生加工链，同时挂载 8,192 种无关的同物品 NBT 库存：
Graph 首笔 2.19 ms、重复中位数 1.01 ms；同 JVM MAX_FAST 分别 39.49 ms、32.46 ms。
全部三组计划用料、配方次数、费用一致并通过独立解释器。
该组在大图测试之后执行，属于首次目录请求，JVM 已热；未拿它与另一 JVM 的冷启动比较。

为验证空闲调度边界，探针分别在主线程 START 事件人为等待 20 / 60 ms，再请求新的 8,192 层链。
这是控制主线程可用时间的实验，不模拟真实机器计算造成的 CPU 竞争。

| 人为占用 | Graph 首笔 ms | MAX_FAST 首笔 ms | Graph 捕获等待 ms | 空闲捕获 ms | Graph 完整 tick 最大值 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 20 ms/tick | 131.58 | 148.65 | 0.32 | 16.28 | 22.05（2 个 tick） |
| 60 ms/tick | 813.28 | 163.12 | 675.08 | 0.00 | 64.05（12 个 tick） |

60 ms 组的空闲批次为 0，最长捕获批次 0.88 ms；已超时的服务器没有继续使用空闲额度。
代价是该情况下首次 Graph 明显慢于 MAX_FAST。本次没有为追赶旧算法而提高忙服捕获额度。
该组 MAX_FAST 窗口内两个完整 tick 最大 62.34 ms；不能把人为造成的低 TPS 归因于捕获优化。
人工负载在测试后显式恢复为 0，也有 600 tick 自动清除机制。

## 计时字段

开启 `ae2GraphDiagnosticLogging` 后，`[Graph Crafting] plan` 新增：

- `snapshot_idle_ms`：主线程在等待下一 tick 的空闲阶段实际捕获的时间。
- `snapshot_tick_slices` / `snapshot_idle_slices`：两个阶段执行的工作批次数，不是游戏 tick 数。
- `snapshot_max_slice_ms`：最长一次捕获批次；不含构造捕获对象之前的准备阶段。

原有 `snapshot_ms`、`snapshot_elapsed_ms`、`snapshot_wait_ms`、`catalog_prepare_ms`、
`planner_ms` 和 `plan_assembly_ms` 继续用于区分实际工作、等待及后台处理。
测试探针的完整 tick 统计不包含边界半个 tick 和两 tick 之间的空闲阶段，不能单独证明整个请求没有卡顿。
