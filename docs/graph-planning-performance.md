# 图规划开销与 MAX_FAST 对照

2026-09-23，Java 21.0.3，Forge 47.3.7，AE 15.4.10，6 GiB 堆，加载实际
`gtladditions-3.2.8Custom_SubSpace-fix2.jar`。本轮是在完整图引擎、合成环 UI 和并行修复基础上的后续优化。

## 为什么快照会等下一 tick

当前 Core 的 MAX_FAST 已经绕过原版 AE 规划的 tick 握手：`simulateFor()` 只检查是否完成，
`handlePausing()` 只检查中断。计算在原有后台线程持续推进。
`NetworkCraftingSimulationStateMixin` 也跳过完整库存复制，持有 AE 的缓存引用，在求解时按需读取。
启用模拟提取或存在手动预留时，还会调用实时库存的 `extract(SIMULATE)`。

图引擎同样在后台持续求解，但目录捕获、输入有效性查询和库存模拟提取在主线程完成。
`GraphSnapshots` 的增量捕获共用每 tick 2 ms 额度；超过后保留当前位置，下个 tick 继续。
因此一次实际耗时约 2.3 ms 的热快照可能多等待接近 50 ms。
这个额度是增量操作之间的让出条件，不能中断单次附属调用，也不代表主线程任意调用都严格小于 2 ms。

MAX_FAST 也要生成计划、统计次数和 bytes，并非没有组装成本。
图计划还要保存压缩执行步骤、种子回收约定并验证物料序列，单看 `planner_ms` 会漏掉验证和最终 AE 计划组装。
比较采用从请求到 future 完成的总耗时。

可以继续异步化捕获后的数据处理，但不能把共享 `KeyCounter`、实时存储或任意附属 `IPatternDetails`
直接交给后台线程，假定它们不发生变化。当前优化保持这些世界接口的线程边界；提交时仍核验有效样板并实际取料。

## 本轮修改

- 将库存捕获的状态机调度摊到每批至多 32 个键，保留每个键的取消、限额和 tick 截止检查。
  仍查询空缓存键，避免刚插入的原料尚未进入 AE 缓存时被当成不存在。
- 借鉴 MAX_FAST 的普通节点批量推进方式，对确定的 DAG 算术及序列摘要每次推进至多 32 个操作。
  保留中间状态、逐操作限额、BigInteger / 受检 long 算术和最终物料验证；循环选择逻辑未改。
- 最终计划保留自身持有的只读哈希表，避免用 `Map.copyOf` 再次构造样板映射。
  JFR 的 61 个图规划线程样本中，25 个落在 AE 计划组装，多个栈命中 `MapN.probe` / 样板 `equals`。
  这是定位依据，不能把有限采样比例当成精确 CPU 占比。
- 复用已经统计的配方集合计算逻辑节点费用，减少一次执行步骤遍历。
- 请求内 AEKey 序列化缓存改为有界 LRU，仍最多 8,192 项 / 1,048,576 字符。
  目录很大时可以缓存当前访问的键，不会装满后永远只保留最早的定义。
  只复用不可变键的编码；每次仍读取样板当前语义，指纹格式不变。

## 新增计时

| 日志字段 | 含义 |
| --- | --- |
| `snapshot_ms` | 捕获准备及增量捕获实际占用的时间 |
| `snapshot_elapsed_ms` | 主线程开始准备到快照完成的经过时间 |
| `snapshot_wait_ms` | 上述经过时间减实际工作时间；主要是 tick / 队列等待及调度开销 |
| `plan_assembly_ms` | 已验证图计划转为 AE 计划、配方统计与 bytes 计算的时间 |
| `phases` | 分阶段实际工作时间，含独立 `VERIFY` 与 `COMPLETE` |
| `wall_ms` | 整个规划请求经过时间，用于用户等待时间对照 |

`planner_ms` 沿用已有口径，不能与其他字段简单相加作为总耗时；并行阶段的活跃时间也可能重叠。

## 测量方法

用 `tools/graph-server-probe` 在隔离服务端执行 `graphstress100m` / `graphstress3b`。
同一 JVM、同一库存、同一样板下串行比较旧 MAX_FAST 与 Graph，交替执行顺序。
每种拓扑 1 次首次请求 + 7 次热请求，首次和热中位数分开记录；规划完成后用独立解释器核对物料及产量。
数量分别为 1 亿和 30 亿，仅测规划，不实际生产数十亿物品。

优化前重跑包为 `b9ed101c…`；第一轮为 `cfc9c57e…`；最终本轮包为
`f39ce476dc5c15d244683ac6df8c9b5611b262a7a48c23ef387b00df34a0645c`。
前后测量均启用相同 JFR profile 和图诊断日志。原始日志及 JFR 留在项目 `.local`，不进入发布 JAR。
两包跨 JVM 的前后数据仅作补充；最终新旧引擎的主要对比采用同一 JVM。

## 最终结果

下表为热请求总耗时中位数，单位 ms；每格采用同一 JVM 内的新旧对照。

| 拓扑 | 1 亿：MAX_FAST | 1 亿：Graph | 30 亿：MAX_FAST | 30 亿：Graph |
| --- | ---: | ---: | ---: | ---: |
| 128 层链 | 4.07 | 2.63 | 1.90 | 1.22 |
| 512 层链 | 11.05 | 4.85 | 5.76 | 3.16 |
| 2,048 层链 | 30.32 | 14.84 | 20.63 | 12.37 |
| 8,192 层链 | 76.55 | 62.53 | 72.72 | 64.24 |
| 8 层 × 8 路共享图 | 3.92 | 1.12 | 3.24 | 0.85 |

以上五组目标、原料、缺料、配方次数和 bytes 均一致。另有 16 / 24 / 64 层共享图，
两算法因聚合取整得到不同工作量，仍全部通过独立解释器；不把它们当作等工作量加速。
共 16 组、128 对请求，双方所有计划的解释验证通过，超过 int 的数量没有截断。

本轮重跑的优化前 Graph，1 亿 / 8,192 层热中位数为 130.45 ms，最终为 62.53 ms（减少约 52.1%）。
这条是跨 JVM 的补充前后对照，MAX_FAST 在两次 JVM 的同组中位数分别为 78.44 / 76.55 ms。
其他组不保证每项都变快，例如 128 层跨 JVM 的 Graph 中位数为 2.51 / 2.63 ms。

快照跨 tick 尚未完全消失。1 亿 / 8,192 层的七个热请求中仍有两个明显等待；
最终总耗时范围 59.01～111.99 ms，旧 MAX_FAST 为 70.36～86.62 ms。
30 亿同组最终范围 52.05～108.65 ms，旧为 66.23～78.14 ms。
热中位数优于旧算法，不等于尾延迟已经全面更好；七个样本不足以给出稳定 p95 承诺。

最终日志的一条实际快照工作为 2.1695 ms，经过 50.0895 ms，等待 47.92 ms；
同组热等待中位数为 0.0118 ms，AE 计划组装中位数为 14.6661 ms。
`snapshot_ms` 包括准备阶段，与增量捕获自身的 2 ms 额度不能直接画等号。

**首次捕获仍是主要短板。** 1 亿 / 8,192 层首次请求 Graph 为 3,231.71 ms，旧 MAX_FAST 为 304.92 ms。
其中快照实际工作约 134.14 ms，经过约 3,151.37 ms，大部分是在等待主线程的下一份额度。
优化前同组 Graph 首次为 3,861.25 ms，本轮有下降，但仍远慢于旧路径。
随后 30 亿的同拓扑重新安装了提供者，目录复核仍需约 3,692.75 ms，不能称作全新 JVM 冷启动。
后续的大幅改进需要将样板的有效语义捕获与纯指纹/索引构建分离，后者在不可变副本上异步执行；
此次没有通过放大主线程额度或后台直接调用实时库存来隐藏这个差距。
