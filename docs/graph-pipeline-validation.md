# 循环任务的流水线执行器（2026-09-24）

本轮接续 [无限水回路修复](graph-water-byproduct-validation.md)。旧图执行器切换配方前等待上一阶段
全部产物返回，导致一批慢机器拖住已经具备实物材料的下游。本轮允许含环任务跨阶段推进。

## 调度与物料约束

纯无环平铺计划继续使用已有就绪队列。其余计划从原来的压缩执行见证中预取最多 32 个批次，
按轮转顺序检查可以开工的步骤；相同配方的多次出现优先使用最早的未派发次数。
`Repeat` 不按订单数量展开，1 万亿轮的持久状态仍只有一个有限窗口和剩余游标。

放行同时要求：

- 输入来自 CPU 实际持有的库存，预计产物不能投料。
- 提前执行后，较早的未派发步骤仍有足够的材料完成；这包括已经接受、等待返回的真实批次。
- 较早步骤的数量峰值不会超出 `long`；提供者缩小批量时，放行条件仍须成立。
- 沿用提供者容量、CPU 派发额度、能量和在途批次数限制。

检查只涉及候选配方改变的资源，以及窗口内位于它之前的步骤。设这些前序步骤为 P，
候选批次为 B，则提前派发后，持有量与已承诺回料之和必须覆盖 P 的前缀需求，
并为 P 的峰值保留空间。P 完成后，未执行的 B 和后续步骤仍保留原计划的物料净变化。
因此不能仅凭“当前有一个种子”就让后面的消耗配方抢走恢复循环所需的材料。

已接受批次的输出义务始终保留。部分回料可以让其他步骤开工；订单最终交付仍须等全部义务结清，
并确认保种要求满足。取消只退还真实持有材料，后到的机器产物按原逻辑进入网络。

检查次数与成功派发次数分开计费，暂时缺料的候选不会占用一次成功派发额度。
每次执行器 tick 仍受约 2 ms 工作片与最多 4096 次检查约束，外部提供者调用本身不能被抢占。

这是有界的局部调度优化，不保证全图最优吞吐；机器故障、缺少承诺产物或窗口之外的依赖仍可能等待。

## 持久化与回归

任务 schema 升为 4，保存前瞻窗口中的未派发次数和后方压缩游标。
恢复时校验两者之和等于计划次数减去已接受次数；schema 1–3 的旧游标可迁移。
任何不明确的输入转移或产物归属都保持暂停，不能因取消旧阶段屏障而自动重发。

测试覆盖：

- 上游部分产物到达，下游在慢批次仍在途时开始。
- 只有一份循环种子时，后面的消耗配方不能抢走它；额外富余的种子可以使用。
- 提供者忙时，独立分支可以继续；缺料候选不消耗成功派发额度。
- 无关副产物延迟返回时，下游能开工，但订单不能提前结清。
- 重复计划、随机回料顺序、运行中多次保存恢复，以及混合阶段在途时取消。
- `Long.MAX_VALUE` 附近的中间峰值、1 万亿轮压缩计划、真实 AE 物品/流体键和 NBT。
- schema 3 的部分执行任务迁移，损坏窗口计数和不明确的批次归属。
- 原有拒绝、回调中保存、供应器异常、结算异常及重规划回归。

200 组随机见证使用独立物料账本逐笔核对投料、回料、最终交付、余料和每张配方的准确次数。
最终构建：图核心 26,494 条、既有运行时 200 条、流水线测试 43,717 条断言通过；
真实 AE 接口集成、格式、Mixin 包检查及完整构建通过。

## 受控执行对照

同一个 `GraphPipelineTest` 主程序分别加载前版生产 JAR 与新版类。
循环为 `C + R → I → J → C + P`，100 轮；每次供应器接收 1 份，每 tick 最多派发 8 次。
上游交替耗时 1 / 12 tick，另外两步各 3 tick，实际返料事件才增加独立库存。
测试主动随机保存恢复；表中的 tick 包含调度和最终结算。

| 种子数 | 订单数量 | 前版图执行器 | 新流水线 | tick 减少 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 100 | 1551 | 1551 | 0% |
| 2 | 200 | 2101 | 1561 | 25.7% |
| 4 | 400 | 2101 | 1561 | 25.7% |
| 8 | 800 | 2101 | 1562 | 25.7% |

种子只有 1 份时没有物料允许额外重叠；增加窗口不会创造种子。
新版检查的 CPU 开销有所增加：这轮 2 / 4 / 8 种子测试，执行器累计活动时间约 7 / 12 / 20 ms，
前版约 5 / 7 / 14 ms。这些短测试受 JIT、调度与同时运行的验证进程影响，只作为开销量级，
不能将游戏 tick 缩短解释成 Java 计算时间同等下降。

原始记录：`.local/benchmark-pipeline-before.log`、`.local/benchmark-pipeline-after.log`。

## 服务端验证环境

隔离 Forge 47.3.7 服务端，Java 21，AE2 15.4.10、ExtendedAE 和用户的 ADD
`3.2.8Custom_SubSpace-fix2`。真实 AE CPU、真实无限水元件、样板注册、网络出入料与新旧执行器参与。
处理机器由确定性的测试供应器模拟；不是对用户未知的 GT 机器故障的复现承诺。

新增 `case=pipeline` 让上游交替延迟 1 / 60 tick，观察下游投料时是否仍有上游半成品在途。
前版图执行器该场景为 16.200 秒，`pipeline_overlap=false`。
新版为 9.199 秒，`pipeline_overlap=true`，订单完成时间减少约 43.2%（约 1.76 倍速度）。
两边均投料 18 次、消耗 9 份原料与 9000 mB 水、产出恰好 9 份目标；没有通过少执行配方缩短时间。
执行器累计活动时间约 6.32 → 6.91 ms，主要收益来自减少机器之间的等待。

最终汇总为 `passed=34 failed=0 max_fast_passed=33 max_fast_failed=0`；
9 个图执行任务和 8 个旧执行任务实际完成。新图引擎比旧对照多一组后缀重规划。
MAX_FAST / AE 的旧执行器在流水线用例中也能重叠，作为兼容性对照保留；其规划一次提取的水量
与图计划不同，不能把两者的完成时间直接作为相同物料调度的性能比。

原始记录：`.local/server-pipeline-before.log`、`.local/server-pipeline-after.log`、
`.local/pipeline-results.json`；完整构建日志 `.local/validation-pipeline-final.log`。

重规划测试在已有不同阶段批次接受后修改下游有效样板，保留旧在途产物义务并验证最终材料守恒。
其延迟与触发条件比前一轮更严格，不用于与前一轮比较用时。
