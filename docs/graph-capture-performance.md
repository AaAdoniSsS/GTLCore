# 图合成首次下单捕获优化

后续空闲阶段捕获与精确输入优化见 [第二轮报告](graph-idle-capture-performance.md)。

2026-09-24，基于 `feat/ae-cycle-support` 的 `863ab023`。
本轮针对第一次请求的目录捕获，补充中英文催化剂配置说明。
此前的异步输出修复及大图缓存修复见 [上一轮报告](graph-large-and-async-output-validation.md)。

## 原因与修改

原先主线程除了读取实际生效的样板和库存，还负责序列化 NBT、计算 SHA-256、构造配方标识及去重。
这些纯计算也占用全局 2 ms/tick 的捕获额度，使几百毫秒的实际工作分散到几秒甚至十几秒。
MAX_FAST 没有同样的主线程分段捕获过程，因此首次请求仍有明显优势。

现在主线程复制样板的确定值和归一化结果，后台工作线程负责编码指纹、构造配方、去重、排序和建立索引。
样板提供者、`IInput.isValid()`、容器返还及库存方法仍在主线程调用；后台只保留不调用的原始样板句柄。
完成后的编译目录原子发布，随后释放临时捕获的配方记录，避免缓存长期保留两份变体数据。
提供者变化后的依赖比较改用捕获值及优先级，不必先编码成字符串再比较。

同时减少 NBT 小对象编码时的临时分配，并省去执行摘要中单次序列的重复遍历。
指纹字符串格式、配方标识、物料验证、提交前检查及全局 2 ms/tick 捕获额度保持一致。
这次没有将实时 AE 库存查询移到工作线程。

## 测试条件

- 项目内隔离 Forge 服务端，Java 21.0.3、Forge 47.3.7、AE 15.4.10、6 GiB JVM 堆。
- 安装实际 `gtladditions-3.2.8Custom_SubSpace-fix2.jar`，SHA-256 为
  `c859ac4953cbc23c3acb3819b78c7d86123da479522b2548e51dbb7d5d22edd8`。
- 修改前使用已发布的 `863ab023` 构建，SHA-256 为
  `ee9551017979d957619e1398919b9bec56eff97f26235b8cace017c18404b28d`，本轮重新跑对照。
- 前后分别启动 JVM；相同工作负载、顺序、JFR profile 和诊断日志。
  每个 JVM 内串行交替执行实际 MAX_FAST 与 Graph 规划，使用独立解释器核对计划物料和执行次数。
- 每笔请求数量为 `1,000,000,000,000`，只测试规划，不实际制造一万亿物品。
  每种拓扑一次首次请求及四次重复请求；65,536 层为一次首次及两次重复请求。
- 32,768 层以内使用默认 32 MiB 请求预算；65,536 层仅在测试服运行时调到 128 MiB。
  节点工作限额设为一千万，工作线程为 4。发布默认配置没有提高。

## 首次请求

表中为调用到得到完整计划的经过时间，包含捕获等待，单位 ms。

| 拓扑 | 修改前 Graph | 修改后 Graph | 减少 | 本轮同 JVM MAX_FAST |
| --- | ---: | ---: | ---: | ---: |
| 8,192 层链 | 4134.15 | 1533.97 | 62.9% | 499.89 |
| 16,384 层链 | 5449.40 | 1718.25 | 68.5% | 308.70 |
| 32,768 层链 | 9465.34 | 2924.26 | 69.1% | 644.82 |
| 512 层 × 32 路共享依赖 | 7426.80 | 2740.34 | 63.1% | 637.70 |
| 65,536 层链 | 17957.50 | 6386.60 | 64.4% | 1401.89 |

每种拓扑只有一次首次请求，包含 JIT、GC 和系统调度差异，不能视为稳定的加速倍数。
同期 MAX_FAST 首次时间也比对照 JVM 更短；因此需要结合实际捕获工作量判断改动效果。

主线程捕获实际工作时间（不含跨 tick 等待，取 SNAPSHOT 阶段累计），单位 ms：

| 拓扑 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 8,192 层链 | 179.91 | 54.82 |
| 16,384 层链 | 231.97 | 63.56 |
| 32,768 层链 | 390.91 | 105.79 |
| 512 层 × 32 路共享依赖 | 293.21 | 95.53 |
| 65,536 层链 | 793.29 | 232.12 |

32,768 层捕获实际工作减少约 72.9%，65,536 层减少约 70.7%。
纯编码改在后台执行后，它不再消耗主线程捕获额度，也相应减少跨 tick 等待。

## 正确性与兼容验证

`graphCoreTest` 通过 25,772 项核心断言、178 项运行时断言及调度测试；
`graphIntegrationTest`、Mixin 包检查、格式检查和最终构建通过。
新增测试覆盖原指纹格式的逐项比较，包括数字边界、转义、嵌套 NBT、Forge capabilities、物品及流体。
另一组测试在捕获后禁止调用实际样板方法，验证工作线程不再访问它们，并覆盖输出数组变更、
30 亿输入、配方标识、重复配方、工作限额中止后的重试及两个构建者并发发布。

实际 ADD 服务端验证了 FOA 4/8 倍、容器 4 入 1 回、NBT、30 亿输入和捕获后指纹一致。
实际超级样板总成的 4 倍计划需要 2 原料生产 8 产物；改为 8 倍后，旧计划以
`PATTERN_FINGERPRINT_CHANGED` 在取料前拒绝，库存仍为 100、CPU 空闲。
重新规划需要 1 原料生产 8 产物。相同依赖的提供者同 tick 移除/添加仍可复用目录。

通配符实际展开为 264 个条目、263 份不同样板。初次测试因为假定所有展开项不同而失败；
比对完整捕获值后确认其中两项均为 `gtceu:ruridit_dust + minecraft:coal → gtceu:ruridit_ingot`，
连样板定义、输入、输出、倍率及返还物都完全相同。修正夹具以允许完全相同的展开项，
仍拒绝不同语义的指纹碰撞；全部不同样板的捕获指纹、双配方回收环、精确种子/燃料、
无种子拒绝和修改产物后的指纹变化均通过。

实际 AE CPU 经外部处理提供者和真实异步输出总成的取消测试通过：
初始 1000 原料，派发一批后取消，迟到产物返回后剩余 999 原料、1 产物。
该路径还覆盖先拒绝入库、随后每次最多接受 7 个，以及缓冲区 NBT 保存/加载。
这是可控外部处理夹具，不等同于运行整套 GT 巨构配方。

所有压测计划均通过独立解释器，修改前后 Graph 物料与执行次数保持一致。
需要保留两类区别：

- 共享依赖中 MAX_FAST 使用 `1000000015212` 原料，Graph 使用 `1000000007816`，两者都合法。
- 65,536 层费用的精确公式为 `(2 × depth + 1) × amount + 8 × (depth + 1)`，结果为
  `131073000000524296`，Graph 与其一致。旧算法用 double 累计，结果少 8 bytes；
  日志保留 `bytes_equal=false`，没有把它描述成物料丢失，也没有计为两算法完全相同。

捕获记录增加了每个实际样板 64 字节的预算估算；65,536 层累计估算为 66,584,712 字节（约 63.5 MiB）。
这是请求数据结构的累计估算，并非 JVM 真实保留堆内存。后台完成后释放临时记录，
但没有据此宣称新旧算法的实际堆占用比例。

## 计时与剩余开销

启用 `ae2GraphDiagnosticLogging` 后，`[Graph Crafting] plan` 新增 `catalog_prepare_ms`，
统计后台编码、目录排序及索引建立的实际执行时间。
已有 `snapshot_ms` 是实际捕获工作，`snapshot_elapsed_ms` 是捕获开始到完成的时间，
`snapshot_wait_ms` 是两者差值，`plan_assembly_ms` 是最终 AE 计划组装时间。
各指标有包含关系，不能直接把所有数字相加。

65,536 层首次捕获经过约 5301 ms，其中等待约 5069 ms；后台整理约 481 ms，计划组装约 122 ms。
剩余主要瓶颈仍是必须在主线程执行的样板回调、归一化和库存采集，经 2 ms/tick 分段后产生的等待。
之后可继续减少重复回调及捕获步骤；直接在后台读取可变实时库存不能替代这部分正确性边界。
